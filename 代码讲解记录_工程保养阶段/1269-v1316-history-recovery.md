# v1316：权重回到第二步，日志也必须知道第二步在哪里

## 一、这次问题不是 checkpoint 又坏了

前几版分别补了随机状态、检查点安全写入和分词器身份校验。这些改动让恢复出来的模型更接近我们想恢复的那一个模型，但训练目录里还有另一类状态：指标日志。训练入口会先写评估结果、曲线和统计摘要，最后才提交 checkpoint。如果第三步的评估记录已追加，随后保存模型失败，第二步的检查点仍完整存在，日志却已经走到第三步。

旧实现再次从第二步续训时，只负责追加新一轮第三步记录，原来那条没有成功对应到 checkpoint 的第三步记录仍在文件中。真实小训练复现出的步骤列表是 `[2, 3, 3]`，而不是 `[2, 3]`。曲线可能重叠，记录数会多一次；更重要的是，统计器不知道哪一次评估属于已经提交的模型状态。这不是测试框架虚构的错误，而是两个保存时机之间的真实缝隙。

## 二、用可验证的前缀定义提交边界

本版为新 checkpoint 增加可选的 history_state，其中包括版本号、日志的字节长度和这些字节的摘要。检查点写入成功以后，这三个字段就跟模型状态一起固定下来：它们说明，在这份模型提交时，指标文件有哪些字节已经存在。恢复时不再凭日志最后一行的步数猜测，而是先核对这个已提交前缀。

选择字节而不是记录数，是因为末尾可能只写入了半行 JSON，甚至只有半个中文字符。若先把全文件当作文本解析，这些尚未提交的尾部内容就足以阻断恢复。前缀长度让程序先定位边界，摘要则确认边界以内没有被替换或编辑。长度相同不代表内容相同，所以两个条件都需要；仅凭记录数也不能发现某条历史 loss 被改了。

## 三、为什么不是按 step 小于等于检查点步数过滤

按步数过滤看起来更简单，但它要求所有行都能解析，还可能在同一步多次评估时误判哪些记录属于提交状态。单独修改过滤条件也无法证明旧内容没有漂移。比如有人调整过第二步的记录，再把第三步删掉，最终步骤列表仍然很好看，却已经不是 checkpoint 当时对应的那份历史。修复不能为了得到整齐的列表而偷偷创造新的证据。

本版保留原始行尾、空白和记录顺序，不重新序列化已经提交的日志。校验通过后取原文件的精确字节切片，因此中文、换行风格和已有 JSON 格式都不会因为恢复而变化。生产入口生成检查点前已使用既有加载器读取日志，本版没有改变 TrainingRecord 的字段，也没有给科学实验的结果增加另一套解释规则。

## 四、几个文件各自负责什么

training/history_recovery.py 新增快照与恢复两个主要函数。快照读取当前日志，返回小型状态字典；恢复接收日志路径与 checkpoint，先检查字段，再检查已提交前缀。它只负责文件恢复，不计算 loss，不决定实验是否通过，也不接管训练循环。原来的 core.history 继续负责追加、加载、汇总和绘图，没有为了这次修复去改变历史消费者。

scripts/train.py 把恢复调用放在模型状态加载和目标步数检查之后、输出目录准备和文件写入之前。这样分词器不匹配、模型参数不兼容或目标步数无效，都不会先触发日志回退。真正开始新一轮训练之前，再按既有顺序恢复随机状态。保存时则在原来的 checkpoint 字典中加入日志快照，不调整采样与随机状态捕获的位置。

## 五、先保留完整原件，再替换活动日志

发现额外尾部后，恢复函数不会直接截短原文件。它先计算整个当前日志的摘要，用前十二位组成备份文件名，再把全部原始字节保存到同一目录中的备份。备份不仅包含被排除的尾部，也包含原来的前缀，方便人独立检查一次失败尝试到底留下了什么。只有备份完成，才发布恢复后的活动日志。

这些备份是用户的运行证据，不是可以由例行清理随手删除的缓存。训练读取的是固定的 metrics.jsonl，不会把备份混入统计。相同原始字节对应相同备份名，使中途失败后的重试不必再制造一份同内容副本。如果这个名字已经存在，代码还会比较完整字节；发现不同内容就停止，不会把名称相同误当成内容一定相同，也不会覆盖冲突文件。

## 六、为什么要提取原子写入引擎

v1314 已经有可靠的 checkpoint 文件写入流程：在同目录创建唯一候选文件，写入、刷新、同步并关闭，最后替换目标。本版既要保存恢复备份，也要更新活动日志，继续复制两遍相同流程会让将来的修复越来越难同步。因此把这段行为提取为 write_atomically，原来的 save_checkpoint 变成一个很薄的调用方。

共享引擎接收路径与写入回调，并不关心回调写的是 Torch 序列化结果还是日志字节。它保留候选文件的所有权、关闭顺序和异常清理，数据如何表达则由调用方决定。原有 checkpoint 故障注入和强杀测试继续原样运行，保护这次提取没有改变旧承诺。共享的不是一个不断增加业务参数的巨型保存函数，而是范围明确的文件发布行为。

## 七、恢复中的第二次失败怎么处理

恢复本身也可能失败：备份无法发布，或者备份已经保存成功、活动日志替换失败。前一种情况必须保留完整原始日志，不能因为备份失败还继续截短；后一种情况则同时保留原始日志与已经完成的备份。测试分别让这两个替换位置抛出异常，检查原文件字节不变，且正常展开调用栈之后没有本次写入候选文件残留。

撤销故障后再次调用恢复，第二种情况会遇到已经存在且内容相同的备份。此时应该复用它，再完成活动日志替换。恢复完成后重复调用又应成为无操作，不重复生成文件，也不改写已提交字节。这就是本版幂等性检查的具体含义，而不是只在说明中写一个“支持重试”。异常始终向调用者传播，不会被吞掉后打印训练成功。

## 八、损坏的前缀必须拒绝，而不是自动修理

新元数据存在时，版本必须是支持的整数版本，字节长度必须是合法整数并位于当前文件范围内。缺失文件、被截短的文件、同长度但内容被改过的前缀，以及损坏的摘要，都无法证明与 checkpoint 的对应关系。此时恢复函数拒绝继续，并保持现有目录内容不变，不先创建一个可能让人误以为修复完成的备份。

测试把无效版本、布尔值、负长度、字符串长度和错误摘要组织成数据表逐项检查，而不是为每一种错误再生成一套相似测试文件。另一个表分别覆盖前缀被替换、变短和整份文件丢失。所有场景都会比较目录中的文件名与字节，避免只断言出现 ValueError，却漏掉函数在报错前已经修改数据的问题。

## 九、真实续训链路的证据

集成测试从已有 tiny checkpoint fixture 出发，真实运行到第二步，再把第三步的模型保存注入失败。它先确认旧 checkpoint 字节仍完整，保留这时的全部日志，再重试到第三步。修复后的活动日志只包含第二步与第三步，摘要的 record_count 也回到两条；同时新产生的备份必须逐字节等于重试前的失败日志。

另外两个入口测试保护拒绝顺序与范围。一个在成功保存第二步之后破坏已提交前缀，要求重试报错且所有运行文件不变。另一个显式选用新的输出目录，要求原目录连未完成尾部也保持原样，新目录则维持旧入口的行为，从本次续训开始记录。它们分别证明“该拒绝时没有提前写入”和“不能借恢复之名修改另一份运行历史”。

## 十、旧 checkpoint 与新目录的边界

历史 checkpoint 没有 history_state，无法知道过去的哪一段日志确实对应当时模型。如果根据当前文件补造一个标记再宣称验证成功，就是把未知事实写成已知事实。本版选择保持兼容：缺少字段时不自动修理，新的成功保存才会增加真实边界。旧文件仍能加载，但不能据此获得从未记录过的历史一致性保证。

同样，本版只处理在 checkpoint 原目录中恢复的情况。另存到新目录可能代表用户有意开始另一条实验分支，不应该暗中导入原日志或改写原目录。不同输出目录保留以前的行为；这不等于解决了任意目录合并、多人并发训练或运行分支管理问题。明确限制作用范围，也使自动回退只发生在用户实际选择恢复的同一份运行状态上。

## 十一、测试代码也需要克制

前两版各有一段小模型续训参数，本版出现第三个相似场景时，不再复制新的参数列表，而是在已有 model_cli_fixtures 中提取 tiny_resume_args。两个旧测试改为调用它，所有参数值和原有断言保持不变。用语法树对比检查旧断言、旧参数列表和 make_tiny_checkpoint 函数体，确认提取没有顺便改变 fixture 或削弱测试要求。

新版的生产增量主要是一个小恢复模块和原子写入函数的提取，没有把训练入口扩大成文件事务框架。原有随机续跑、分词器绑定、checkpoint 故障测试、模型 CLI 与架构边界测试一起组成定向回归。严格类型检查覆盖本次两个生产模块；全仓库仍运行原来的快速检查与覆盖率入口，不修改门槛，也不把历史高覆盖模块归档掉来重新解释数字。

## 十二、最强质疑与复核方式

最强的质疑是：自动恢复是否会删除人编辑过的日志，又把结果包装成正确？对应的防线不是一段保证书，而是摘要校验、先备份再替换、备份冲突拒绝和异常路径的字节断言。若已经提交的字节变了，程序不能擅自决定哪一份正确；若只是未提交尾部多了出来，程序也先保留原件，让后续排查仍有依据。

这仍不是整个目录的事务。曲线、样本、配置和运行清单不会同时原子回退；它们在后续训练成功时按原逻辑重新生成。代码没有提供并发写锁或目录项掉电耐久性，读取与备份也使用与文件大小有关的内存。需要这些能力时，应另立清晰需求与验证，不把它们附会在一次同目录日志恢复上。

在仓库根运行 `python -B -m unittest tests.test_history_recovery tests.test_checkpoint_io tests.test_tokenizer_binding tests.test_rng_state tests.test_resume_rng -v` 可复核主要路径。完整验证仍使用 `scripts/run_test_coverage.py` 和不变的覆盖率门。版本证据只记录命令真实退出结果和对应报告，不能把故障用例内部打印的失败当作整轮失败，也不能提前填入尚未完成的远端 CI 结论。

一句话总结：本版让新 checkpoint 指明已提交日志的真实边界，在保留失败尝试原件的前提下恢复同目录续训，避免旧模型状态与重复的未来指标混在一起。
