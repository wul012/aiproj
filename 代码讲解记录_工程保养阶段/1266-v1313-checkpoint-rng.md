# v1313 训练断点的随机状态与可复现续跑

## 一、版本目标与非目标

本版属于独立 aiproj 的工程线，修复基础训练入口中“能恢复权重，却不能恢复训练轨迹”的问题。原脚本已经保存模型、优化器、配置和步数，恢复时也重新加载了这些内容，但是每次启动都会从命令行种子重新开始随机序列。训练批次从数据张量中随机选择，Dropout 也使用随机数，因此恢复后即使步号正确，下一个批次和掩码仍可能与连续训练不同。此次增加可选的随机状态字段，目标是恢复到下一个训练步骤真正需要的随机位置，而不是只让脚本继续运行。

非目标包括科学实验迁移、归档清理、模型结构变化、提高生成质量或修改历史结论。本版不会执行 v1312 的归档方案，也不降低覆盖率门槛。此前讲解被保存为独立的学习目录，那里是面试学习材料，不替代本篇工程证据，也不承担研究结论。Java、Node 和 mini-kv 不在此次修改范围内，AI 项目不需要它们配合才能进行小规模恢复测试。

## 二、为什么重设种子不等于恢复状态

种子可以确定伪随机序列的起点，但无法代表序列已经消耗到哪里。可以把它想成一本固定的随机数列表：第一次启动从第一页开始，训练几步翻到后面；再次设置同一个种子只会回到第一页，而不是回到中断页。初始化模型会消耗随机数，训练选取批次会消耗随机数，注意力和前馈层的 Dropout 也会消耗随机数。仅加载权重和 AdamW 的动量，并不能把这些随机源的位置恢复过来。

因此测试特意使用非零 Dropout。若全部关闭随机操作或只比较输出形状，恢复逻辑很容易看起来正确。旧实现的验证在第一、第二、第三和第五步分别中断，再继续到第六步，四个场景都出现了模型张量不相等。它们共用同一套断言，不是先修改期望再让测试变绿。失败只来自新增的轨迹一致性检查，旧 checkpoint 可加载这一条在修改前也正常。

## 三、状态由谁保存与恢复

新模块 `src/minigpt/training/rng_state.py` 只负责随机生成器状态，不处理模型层、数据质量报告或发布治理。捕获函数返回一份版本化字典，包含 Python random 的状态、NumPy 全局生成器状态、Torch CPU 状态，以及已经初始化的 CUDA 生成器状态。训练脚本只调用这两个短函数，不把各框架的状态操作散布到训练、评估和采样的多个位置。

捕获过程本身不前进随机序列，这是连续训练兼容性的一项关键前提。单元测试连续捕获两次，比较 Python 元组、NumPy 数组和其他状态字段，以及 Torch 字节张量，确认没有变化。另一个测试先捕获、再取随机数、恢复后再次取数，要求三种 CPU 随机源的结果完全一致。它验证的是序列位置，不是分布相似，也不是允许误差范围内大致相等。

## 四、为什么选择训练 owner 包

仓库已经有 core、training、evaluation、serving、reports 和 governance 的职责边界。随机状态续跑属于训练运行时管理，放入 training 包不会让底层模型依赖报告或治理模块。模块没有重新占据巨大的 flat namespace，也没有扩展根包的公开导出列表。现有 import 路径、历史兼容 facade、科学实验入口以及 frozen fixture 均保持原样。

新的生产模块很短，行为分别集中在捕获和恢复函数中；测试分成随机状态单元测试与真实训练流程测试，而不是按每个测试场景复制一套生产 helper。这样既能直接测状态序列，也能从训练入口发现调用时机错误。两种证据必须同时存在：只测 helper 不能证明主脚本确实使用它，只测训练又难以区分错误来自 NumPy、Torch 还是检查点时序。

## 五、恢复为什么放在初始化之后

恢复入口仍然先读取 checkpoint 和 tokenizer，再构造模型与优化器并加载各自状态。模型构造本身会随机初始化参数，即使这些参数随后被已保存权重覆盖，构造过程消耗的随机数也不会自动退回。如果过早恢复随机状态，再创建模型，序列位置会立刻被初始化操作推进，下一批数据仍然不一致。因此恢复放在准备工作完成后、真正进入训练循环之前。

这时数据已经编码、输出目录与数据说明已经处理，接下来就是选取训练批次。没有随机字段的旧 checkpoint 走空操作路径，沿用原先种子恢复方式；它可以继续训练，但不能宣称找回过去未保存的序列。新格式使用版本号区分解释方式，遇到未知随机状态版本会明确报错，而不是把无法识别的数据当成功恢复。这里仍使用现有的可信 checkpoint 加载机制，不把它宣传成不可信文件的安全沙箱。

## 六、训练结束时的额外评估陷阱

基础脚本会在第一步、固定间隔和最后一步计算训练及验证损失。假设评估间隔为两步，完整训练到第六步会在第一、第二、第四和第六步评估。如果先训练到第三步，脚本还会因为“第三步是本次最后一步”多做一次评估。这次额外评估同样通过随机批次计算均值，消耗 Torch 随机数，但连续训练在第三步不会做它。只在脚本最后保存当前随机状态，仍无法让恢复轨迹与连续训练一致。

本版把计划内评估和只因结束而出现的评估分开。当最后一步不在计划评估时刻，就在这次额外评估前捕获续跑快照；如果最后一步本来就是计划评估，则保留评估原有的随机消耗，再捕获状态。这种处理没有把所有评估改成随机隔离，也没有改变未中断训练的行为。它只选择正确的恢复边界，使下一次进入循环时读到与未中断路径相同的位置。

## 七、采样和报表为什么不能决定续跑位置

训练结束后还可能生成样本文本。采样使用概率分布和 multinomial，会继续消耗随机数；是否要求写出样本，不应决定下一次训练选到哪个批次。因此续跑快照必须在末尾采样之前固定下来。快照保存在 checkpoint 中，而不是假定保存文件时进程的随机状态就是下一个训练步应有的状态。报表、样本和续跑是三个不同用途，不能仅因为它们在同一个函数尾部就混用状态。

测试默认打开末尾采样，并使用非空提示词和 top-k。这样能够抓住“权重恢复正确但样本生成把序列推进了”的错误。本版没有承诺分段运行的全部文件逐字一样：分段训练可能多出停止点的评估行，时间戳和运行清单也自然不同。需要完全比较的是模型张量、优化器内部状态、最终损失，以及相同结束条件下的生成样本，而不是把所有元数据当作无关噪声强行抹掉。

## 八、端到端检查比较了哪些内容

新的恢复测试使用临时目录中的短文本，构建一层、两头、八维的小模型。完整路径训练六步；分段路径分别在第一、第二、第三和第五步保存，再恢复到六步。相同数据、词表、批大小、评估间隔、学习率和种子保证比较有定义。Dropout 为零点二，评估每两步发生，生成样本为三个新 token，既覆盖计划内停止，也覆盖计划外停止。

断言逐层检查模型字典中的每个张量，使用精确相等而不是放宽容差。优化器字典也递归比较，包含动量、平方梯度估计、步计数和参数组配置。最终训练损失直接比较，生成样本按文件字节比较。单看某一层权重或最终损失可能漏掉状态不同但短期输出接近的情况，因此这里不把相近曲线当作恢复正确的充分证据。

## 九、旧文件兼容与序列化

兼容性测试从真实小训练产物中移除新增随机字段，模拟旧 checkpoint，再执行恢复。要求它能加载、推进训练步数并产出运行清单，而不是为旧格式补造一个看似真实的状态。新 helper 还通过内存中的 torch.save/torch.load 完成一次序列化往返，确认重新读取的状态能复现后续随机数。测试使用自己的临时文件，不修改历史检查点或提交的科学缓存。

随机状态中的 Torch 字节张量必须在 CPU 上交给生成器设置函数。训练 checkpoint 读取时可能使用 map_location 将模型张量映射到 CUDA，所以恢复 helper 显式把生成器状态移回 CPU。模型权重的设备位置与随机状态 API 的输入要求不是同一概念。这个处理不改变模型设备选择，CPU 和 CUDA 之间的模型数值也没有因此获得跨设备逐位一致保证。

## 十、CUDA 覆盖的实际范围

捕获时只读取已经初始化的 CUDA 状态，不能因为 CPU 训练保存 checkpoint 就突然初始化 GPU。未初始化时该字段为空；读取带 CUDA 字段的 checkpoint 而当前运行环境没有启用 CUDA，也不能自动触发设备创建。测试分别覆盖了未初始化时不调用 CUDA 捕获、已初始化时调用状态恢复，以及 CPU 环境跳过 CUDA 恢复这几条分支。

本机实际 PyTorch 环境是 CPU 版本，所以 CUDA 分支使用受控 mock 验证调用行为，不把它写成真实 GPU 训练复验。精确轨迹结论只限相同数据、配置和确定性运行环境。不同 PyTorch 版本、设备型号、GPU 数量、内核选择或非确定性算子都可能影响结果。保存随机状态是可复现的必要组成部分，但不是抹平所有硬件和软件差异的万能开关。

## 十一、工程门与已知边界

本版执行新增 unittest、原有模型 CLI 行为和架构分层测试，再执行 CI 中所有快速检查入口以及相同覆盖率入口。检查不改变 baseline 或 floor，也不归档掉高覆盖模块来重新解释总数。v1312 所揭示的维护代码覆盖债仍存在，这一版只补一条真实的训练路径，不能把一次小修宣传成已经偿清全部测试债。安装缺失的验证工具使用本次临时目录，不修改项目的依赖声明。

两篇面试讲解保存在新目录并带索引，源码说明指向实际 core 实现，兼容 shim 不再被误写成唯一实现位置。讲解中的“验证集独立”也补充了极小输入会回退到训练数据的现有边界；此处只校准文字，不偷偷修改数据划分算法。最终暂存采用明确文件清单，个人未跟踪文档和图片不进入提交。任务产生的小模型、测试日志和工具在结果记录后清理，未启动长期训练或服务。

## 十二、复核命令与一句话总结

在仓库根执行 `python -B -m unittest tests.test_rng_state tests.test_resume_rng tests.test_model_cli_behavior tests.test_architecture_boundaries -v` 可以复验局部路径。完整门使用现有 `scripts/run_test_coverage.py` 并保持 fail-under 为八十八点九八；各个 check 脚本的通过依据是自己的 status 字段和退出码，而不是只看没有新告警。发布时保留原来的版本命名方式，只完成本次一个工程版本，后续推进另行安排。

一句话总结：本版让检查点携带下一个训练步骤真正需要的随机状态，并把最终评估和采样产生的额外消耗与续跑边界区分开，从而在明确的环境条件下复现连续训练，而不是仅仅重新加载权重后再开始一条新随机轨迹。
