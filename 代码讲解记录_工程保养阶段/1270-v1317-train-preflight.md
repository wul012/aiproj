# v1317：参数错了，就不要先动已有训练文件

## 一、优化目标从失败时机说起

前几版让检查点保存、分词器配对和日志恢复更可靠，但这些保护都有一个前提：当前请求确实能够开始训练。如果评估次数写成零、验证分片装不下一个 batch，或者采样参数直到最后才被模型发现有问题，程序就可能先更新日志，再迟迟报错。有些错误甚至不直接抛出异常，而是把没有实际评估意义的数值写入报告。只看进程是否启动，无法证明请求有效。

这版只把确定的输入错误提前拒绝，不增加模型能力，不换采样算法，也不扩大成一套训练任务调度系统。目标是让调用者在原始文件仍完好的时候收到能定位参数的错误。对正确请求，随机序列、模型参数、输出内容和默认设置应保持原来行为；如果校验代码让正常训练结果变了，就说明它越过了自己的职责边界。

## 二、两个可复现的旧问题

第一个测试准备一份短语料和已有输出目录，把原来的指标文件、checkpoint 都写入已知字节，再传入 eval-iters 为零。旧入口没有在参数层拒绝，评估循环没有执行任何样本计算，训练仍可继续到文件输出。测试要求出现明确 ValueError，旧实现却没有抛出这个错误。这里不把“没有跑评估也算训练完成”看作正常的兼容行为。

第二个测试使用二十个 token 和原来的九比一划分。训练分片足够，验证分片只有两个 token，达不到当前 get_batch 的长度要求。旧实现先删除已有 metrics.jsonl，再运行训练和评估，直到取验证 batch 时才失败。比较目录字节可以看到原文件消失了。修复后仍然拒绝这份输入，但拒绝发生在删除文件之前；测试的旧数据和保护断言没有改成更容易通过的形式。

## 三、为什么分成两段校验

有些事实从命令行参数本身就能判断，例如 batch-size 是否大于零、train-ratio 是否处于有效区间。这一段不需要读文件，更不需要创建模型，所以直接放在 parse_args 之后。它发生在设置随机种子、加载文本和准备输出路径之前。错误提示使用调用者能看懂的命令行名称，避免让人从深处的 Torch 错误倒推究竟是哪一个开关写错了。

另一类事实必须看到实际输入才能判断。文本先经过字符或 BPE 编码，再按原规则划分，才能知道两个分片的 token 数。它们的最低长度还要使用真实模型的 block_size；续训时这个值来自 checkpoint，不能拿命令行里已经被忽略的新模型默认值代替。因此第二段安排在 tokenization 和 split 之后，但仍早于模型创建、日志恢复和输出写入。

## 四、小模块负责规则，训练入口负责顺序

新增 training/preflight.py 把规则集中在 validate_options 与 validate_splits 中。前者接收已经由 argparse 解析的 Namespace，后者只接收两个长度和有效 block_size。它们不读取路径，不修改参数，不自动补默认值，也不调用模型。这种分工让测试可以检查规则本身，也能检查 train.main 是否在正确位置调用了它们。

相似的整数下限用小型字段表表达，通过一个 helper 统一给出错误信息；浮点有限性由另一个 helper 处理。它不是第二个参数解析器，更不是新的配置对象体系。默认值仍只存在于原 parse_args 中，避免未来改默认学习率时还要找另一处同步。训练入口只增加导入和两个调用，没有继续往一个长 main 中塞几十个条件分支。

## 五、数值边界不能一律写成大于零

批量大小、总迭代目标、评估间隔和评估次数需要正整数。零评估次数会导致没有实际样本的统计，零评估间隔则不能用于取模。学习率不同：零值虽然不会更新参数，但可以用于固定权重的诊断，所以本版保留零学习率，只拒绝负数和非有限值。train-ratio 必须严格处于零和一之间，不通过钳制把错误输入改成另一个请求。

新生成 token 的数量也允许为零。此时模型只保留提示内容，不会执行下一 token 的选择，所以零 top-k 和空提示可以继续保留原有零生成行为。温度仍需要是有限正数，因为原 generate 即使不生成新 token 也会验证温度。这样的规则不是从字段名称猜出来的，而是沿着实际调用路径区分哪些值会被消费、哪些分支根本不会执行。

## 六、NaN 和 Infinity 为什么要单独判断

只检查浮点数是否小于零会漏掉 NaN，因为它与普通数值比较时并不表现为一个正常的有序数。Infinity 在有些运算中也能继续传播很久，直到日志、概率分布或梯度出现异常才暴露。对于学习率、划分比例、启用采样的温度和新模型 dropout，本版先要求有限，再检查对应区间。拒绝的是输入错误，不是通过替换成零去掩盖错误。

测试把这四个选项分别与 nan、inf、-inf 组合起来，并与整数下限、模型维度、seed 范围和采样边界放进数据表。每个子场景都要求错误指向对应开关，同时证明文本加载函数和随机种子设置函数没有被调用。不能只断言出现某种异常，否则它可能是“找不到输入文件”或“模型构造崩了”，并没有证明前置校验实际生效。

## 七、续训时使用的是保存下来的模型

续训入口会从 checkpoint 读取模型结构和 tokenizer，而不是用命令行中的 n-head、dropout 或 BPE 词表大小重新造一个模型。如果对这些已经不生效的命令行值仍做强校验，原本可以恢复的运行就会被无意义地拒绝。生产代码因此只在新训练分支检查新模型和 BPE 建模参数，续训仍把模型有效性的判断交给已有加载与构造流程。

测试给续训请求故意附上很大的 block-size、零 n-head 和 NaN dropout，同时将 tokenizer 开关改为 BPE 并给出无效的新词表大小。因为这些值不参与当前恢复，训练必须仍使用存档中的八 token block_size 并成功推进。这个测试不是鼓励写错参数，而是保护现有接口的有效参数来源，防止校验逻辑在重构时改变模型归属。

## 八、禁用采样就不应该检查采样参数

启用 no-sample 后，温度、top-k、提示文本和生成长度都不会走到 write_sample。于是本版跳过这一组校验，保持此前可用的批处理调用方式。测试把它们设置成如果真正执行采样就会出错的值，再确认训练照常完成。反过来，启用采样时传入零温度、零 top-k 或空提示，就必须在任何输出更新之前被拒绝。

这个分支说明了一个常见工程区别：数据类型正确，不代表参数有意义；参数数值看起来错误，也不一定在当前操作中生效。校验要服从实际执行语义，而不是为每一个字段建立孤立规则。对 BPE 专属参数采用同样做法：当前新训练明确选择 BPE 时验证其词表和频率下限，字符 tokenizer 不会因为不用的 BPE 参数而失败。

## 九、语料长度检查不偷偷修算法

当前 get_batch 要求分片长度至少是 block_size 加二，本版在调用它之前检查相同条件。即使从数学上讨论，某些更短输入也可能构造出一个训练对，那也不是这次改动要决定的问题。放宽最低长度会改变既有数据采样行为，应另有需求和测试，而不该混在一次文件保护优化中。错误信息直接告诉用户哪个分片有多少 token、有效 block_size 是多少。

小验证集的既有回退也保持原样：划分之后不足两个 token 时，当前代码会使用训练分片作为验证数据。前置校验看的是已经完成回退的实际张量长度，不从原始比例推断一个并不存在的验证分片。恢复测试选择会产生非空但不足以取 batch 的验证长度，确认拒绝发生在 history recovery 之前，保留尚未提交的尾部日志供用户排查。

## 十、如何证明旧输出没有被动过

测试对临时根目录做文件名到原始字节的完整快照。失败前后比较这个映射，能同时发现文件被删除、内容被覆盖以及多出新的输出文件。针对 v1316 的联动场景，先真实训练并保存一个带历史标记的 checkpoint，再追加未提交的日志尾部，最后发起带错误参数或错误分片比例的恢复请求。目录必须原样保留，不能先生成备份并回退日志，再说当前请求无法运行。

这些用例只操作临时 toy 数据，不读取或覆盖用户已有训练产物。文件保护限已知的确定性输入错误；合法参数仍可能在随后遇到磁盘空间不足、设备故障或内存不足。本版没有设置资源预算，也不把一个语法上合法但非常大的模型配置宣称为必然可运行。明确剩余风险，才能准确理解前置校验实际解决的是哪类问题。

## 十一、有效路径也要与上一版比较

提前拒绝无效请求比较容易，难点在于不干扰正确请求。独立进程对比使用 Git 中 v1316 的原始 train.py 和当前入口，在相同 CPU 环境、相同短文本、相同种子、dropout 和评估安排下训练。比较完整 checkpoint 数据对象、指标文件、摘要、采样文本和 tokenizer 字节，验证这些新判断没有消耗随机数或重新解释默认设置。

原有的随机续跑、checkpoint 写入故障、tokenizer 绑定和历史恢复测试继续执行，保持此前的保护。新版测试也单独确认 validate_splits 不改变 Torch 随机状态，并保留零学习率、零新增 token 的实际训练用例。对模型本身、旧 fixture、测试期望、覆盖率门槛和科学判定函数没有修改；只新增针对这一类失败时机的规则与证据。

## 十二、证据、边界与复核方法

验证按三层记录：新输入检查的直接测试、包括前几版的定向回归、现有 CI 的完整门。所有快速检查在本地执行；完整覆盖率使用工作流原入口，在同一提交的干净 GitHub 环境中跑完后才打版本标签。报告会分别记录已发生的本地结果与远端结果，不能预填未完成的测试数，也不能把故障子场景打印的失败当成整个测试集的结论。

最强的质疑是“校验是否替用户改了训练行为”。回答它的证据不是模块名字，而是没有修改参数的实现、按有效分支跳过的规则、保留零值的测试，以及与旧入口的数值和字节对比。本版不新增输出目录覆盖策略，不负责识别用户是否选错实验数据，也不将 seed 合法范围误写成完整可复现保证；这些都有独立的需求边界。

在项目根运行 `python -B -m unittest tests.test_train_preflight -v` 可检查前置条件，完整复核入口仍是 `python -B scripts/run_test_coverage.py --out-dir runs/test-coverage-ci --fail-under 88.98`。本版工程说明与机器摘要可以提交，个人面试学习材料仍留在本地并由忽略规则隔离。临时模型、验证工具和日志在结果归档后清理，不为完成检查留下长期运行进程。

一句话总结：先验证实际会执行的输入，再进入模型与输出阶段，让本来可在开头发现的错误不再以损坏旧日志或浪费一次训练为代价。
