# v1314：保存失败时，别把上一份 checkpoint 一起毁掉

## 一、这一版接在什么问题后面

上一版解决的是“从同一个训练位置继续，为什么参数还是变了”。权重、优化器和随机状态都恢复正确之后，在相同运行条件下，分段训练才能接上原来的随机轨迹。这一版检查它的前提：磁盘上是否还有一份完整、可读取的 checkpoint。假如保存新状态时先把旧文件截断，随后磁盘写入失败，那么随机状态字段设计得再完整也没有用，恢复入口连存档都读不出来。

因此，本版只处理训练入口的单文件保存过程，不增加模型层，不改变损失函数、采样安排或科学实验的判定。版本仍采用原来的标签方式，包版本保持不变。它是训练工具的故障保护，不是模型效果提升，也不是对整个运行目录做数据库式事务。先把问题缩小，才能用故障注入准确判断代码是否真的守住了旧文件。

## 二、旧写法为什么有破坏性

原来的调用直接把 checkpoint.pt 作为 torch.save 的目标。成功路径很直观：序列化完成，下一行继续保存分词器和训练配置。但已有文件被打开用于写入时，旧内容可能先被清空；新内容随后才逐步进入文件。如果写到一半抛出异常，文件名仍然存在，却已经不再是上一份完整的检查点。“文件存在”与“文件可用于恢复”在这里不是同一个条件。

红灯测试没有修改已有存档的格式来制造问题，而是先让真实训练入口成功保存第二步，再尝试保存第三步。注入函数向目标写入一段不完整字节后抛出写入异常。旧实现下，测试读到的正式文件就成了这段字节，与第二步存档逐字节比较失败。这一失败才是有效复现；测试草稿曾因小语料验证部分太短而提前报错，那只是测试输入错误，没有被算作产品缺陷的证据。

## 三、新增文件怎样分工

新增的 training/checkpoint_io.py 只负责一个检查点文件的发布。输入是已有 checkpoint 字典与目标 Path，正常完成时不返回额外对象，失败则继续抛出异常。它不判断训练是否收敛，不生成运行清单，也不决定何时保存。scripts/train.py 仍在原来的位置构建包含模型、优化器、随机状态和步数的字典，只把最后的保存调用交给这个小模块。

tests/test_checkpoint_io.py 负责两层证据：第一层直接检查保存函数的文件行为，第二层通过真实训练入口检查它是否真正接入业务链路。测试复用已有的小模型构造函数，不复制第三套模型配置。版本文档保存需求与证据的对应关系；本篇解释为什么这些断言有意义。机器摘要只记录已经运行过的结果，不参与训练，不替代原始测试，也不是新的科学实验结论。

## 四、先准备候选文件，再替换正式文件

保存函数先在目标所在目录创建一个带随机名称的临时文件。名称带有 checkpoint 的前缀便于排查，但不是固定的 checkpoint.tmp。固定名称会让两个调用互相覆盖准备中的内容；唯一名称至少把每一次写入的中间产物隔离开来。临时文件由系统安全创建并立即打开，序列化直接写入这个句柄，不需要先生成一个名字，再用第二次打开去寻找它。

临时文件和正式文件放在同一目录，也让它们处于同一个目录对应的文件系统中，避免跨盘移动退化成复制再删除的过程。新文件完整写好以前，旧文件的路径完全不参与写入。这里的“候选”只是保存流程中的临时内容，不是模型晋级、实验候选或发布审批里的术语，不能因为复用了一个词就把训练 I/O 与科学判定串成另一条流程。

## 五、flush、fsync、close 和 replace 各管哪一段

序列化函数返回后，代码先调用 flush，把 Python 文件对象中尚未交给底层的缓冲内容推出去；随后对文件描述符执行 fsync，要求操作系统同步这个文件的内容。二者不是重复操作：只做后者，用户态缓冲中仍未交出的字节可能根本不在它负责的范围内。测试会在同步故障处主动抛错，确认同步没有成功时不能继续替换旧文件。

离开文件上下文后，句柄关闭，才执行 os.replace。这个顺序也照顾 Windows 上打开句柄与文件替换的限制，不能把关闭文件视为可有可无的整理动作。时序测试在替换发生前检查四件事：候选文件与目标同目录、不是同一路径、候选句柄已关闭、正式文件仍保持原始字节。它还实际读取候选内容，确认准备发布的不是一个只有名字却无法加载的空壳。

## 六、异常清理只能清理自己创建的文件

临时路径开始为空，只有创建文件成功后才赋值。无论序列化、刷新、同步还是替换失败，只要 Python 能正常展开调用栈，finally 都会尝试移除这一次调用创建的临时文件。KeyboardInterrupt 不是普通 Exception 的子类，但 finally 仍会执行，所以没有把清理逻辑限制在只捕获普通异常的分支里。正式文件不会在清理逻辑中被删除。

清理也不能按前缀扫描一批文件然后全部删掉。另一个进程可能正在写同类临时文件，目录中也可能保留着上一轮排错证据。测试专门预置一个相似名称的文件，要求失败前后的目录内容逐字节一致，以证明实现只清理自己拥有的路径。成功替换后，临时路径已经不在原位置，missing_ok 让收尾删除成为无害操作，而不是把正常保存变成“找不到临时文件”的失败。

## 七、故障矩阵为什么要区分首次保存和覆盖保存

矩阵包含临时文件创建、序列化、刷新、同步、替换和键盘中断六个阶段，每个阶段分别在目标不存在、目标已经存在两种情况下运行。前一种保护的是“失败不能留下伪装成完整存档的正式文件”；后一种保护的是“失败不能毁掉最后一次成功结果”。只覆盖第二种情况，可能漏掉首次保存直接暴露半成品的问题；只覆盖第一种，则无法证明旧文件受到保护。

每个场景不仅断言出现异常，还比较整个测试目录的文件名与字节。已有正式文件时，再用 torch.load 检查它仍然对应旧步数。异常类型与注入信息也必须传给调用者，不能被保存函数吞掉后继续打印成功。这些检查共同约束保存函数的可观察行为，而不是仅仅用 mock 证明某个函数名字被调用过。成功路径另测创建与替换，避免把“永远不写文件”这种假修复误判为可靠。

## 八、真实训练失败后还能否重试

集成测试先复用已有的小模型检查点与短语料，通过 train.main 真正训练并保存第二步。随后让第三步的序列化写到一半失败，检查第二步 checkpoint 与分词器字节没有变化，并调用原来的 load_resume_state 加载。这个检查点中仍然带有上一版加入的随机状态，因此不是靠退回一个不完整的旧格式来换取测试通过。

故障注入撤销后，同一个入口再次恢复到第三步，要求正常完成并能读到第三步的存档。测试没有把训练函数替换成假函数，也没有让加载器忽略文件损坏。与此同时，原有分段训练精确相等测试继续运行，保护新保存方式没有破坏随机状态的捕获位置和恢复时机。这里证明的是保存与恢复链路仍然衔接，不是声称失败期间写出的所有日志都自动回滚了。

## 九、强杀进程与普通异常是两种不同故障

为了避免把 finally 的效果夸大为“断电也会清理”，另一个测试启动真实子进程，在候选文件写入不完整内容并刷新后发出就绪标记，然后阻塞在序列化阶段。父进程确认子进程确实到达这个边界，再直接 kill，并等待进程退出。整个检查有超时和 finally 收尾，不会为了测试故障而留下无限睡眠的 Python 进程。

强杀之后，测试要求正式文件仍与旧文件完全相同且可以加载，同时明确断言目录里保留了一份未完成的候选文件。这个残留是预期事实，不应该被报告成“无临时文件泄漏”。测试目录由测试框架在进程结束后清理；生产保存函数没有获得跨进程回收孤儿文件的能力。这个实验只覆盖发布前的受控终止点，不代表已穷举所有崩溃时刻，更不等于硬件突然断电的耐久性验证。

## 十、原子可见性不等于整个目录的事务

本版最容易被质疑的地方是：即使 checkpoint 没坏，metrics、sample 或 tokenizer 是否可能与它不同步？答案是可能。训练入口在保存检查点之前已经运行了诊断和历史输出，检查点之后也还有其他文件写入。本版没有把这些文件组织成一次不可分割的目录发布，因此不能向调用者保证“任意失败后目录全部回到上一刻”。若以后确实需要这个语义，应单独设计版本化运行目录与提交指针，而不是偷偷把它塞进一个小保存函数。

同理，文件同步不等于目录项已经具备掉电耐久性。代码没有追加跨平台目录 fsync，也没有验证网络文件系统的所有替换语义。多个并发写入者仍可能出现最后一次成功替换覆盖前一次结果；随机临时名解决的是准备文件碰撞，不是业务上的写入仲裁。把这些边界写出来，可以避免将一次针对截断风险的有效修复包装成全面的存储事务系统。

## 十一、格式兼容与工程门如何理解

checkpoint 字典的键、模型配置、优化器数据和随机状态结构都没有改变，加载端继续使用原来的 torch.load 路径。序列化从路径参数变成文件对象参数后，压缩容器的内部命名等细节可能不同，因此成功保存的新旧文件不承诺字节完全一样。需要保持的是可加载的数据与训练行为；失败保护则必须逐字节保存原有文件，这两种比较对象不能混淆。

工程验证使用仓库现有的全量 unittest 和覆盖率入口，门槛保持八十八点九八，不修改任何旧测试期望、fixture 或 ratchet。全部快速 CI 脚本也必须在本地逐项执行，不能只选与 checkpoint 名字相关的检查。新增保存模块很小，训练入口只增加一个导入并更换调用点，不借机扩展巨型文件。当前总体覆盖数字仍沿用仓库既有统计范围，不能用它掩盖之前已经记录的维护代码覆盖债。

## 十二、怎么独立复核这一版

在仓库根目录运行 `python -B -m unittest tests.test_checkpoint_io tests.test_resume_rng -v`，可以同时检查保存故障矩阵、受控强杀、训练重试和续跑一致性。全量入口仍是 `python -B scripts/run_test_coverage.py --out-dir runs/test-coverage --fail-under 88.98`。机器摘要记录实际命令、结果和适用范围；远端同提交 CI 通过后，版本标签注释记录提交与运行链接，避免在提交自身内部伪造一个尚未存在的最终提交哈希。

收尾只暂存本版明确列出的源码、测试和说明，不使用宽泛的全部暂存命令。临时工具与报告在结果归档后删除，原有个人文件不动；测试启动的子进程必须已经退出。本版交付的是可独立重跑的实现与证据，是否达到更高等级的整体工程评价仍需要外部复核，而不是由本篇文章给自己授予“最终通过”。

一句话总结：先完整写好候选文件，再替换正式 checkpoint，让一次失败的保存不再连带毁掉上一份仍可恢复的训练状态。
