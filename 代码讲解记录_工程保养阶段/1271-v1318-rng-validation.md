# v1318：确认随机状态能恢复，再改变当前运行

## 一、已有的保护之间仍有空隙

v1313 保存了训练继续所需的随机状态，v1316 又让检查点与指标日志的提交边界对应起来，v1317 把明显的参数错误提前拦截。这些改动各自有效，但放在一起仍需要检查先后顺序。恢复函数当前依次设置 Python、NumPy 和 Torch 随机状态。如果 Python 字段有效、NumPy 字段损坏，函数会先改变 Python 的全局生成器，再在下一步报错，留下一种既不是原状态、也不是目标状态的混合结果。

训练入口还有文件侧的问题：真正恢复随机状态发生在模型和输出准备之后。这样的时机对正确续训是必要的，因为初始化模型本身会消耗随机数；然而，如果一直到这里才发现存档中的 RNG 格式无效，前面的日志恢复可能已经保存备份并改变活动日志。这一版不是把真实恢复简单搬到前面，而是把“校验能否恢复”和“实际安装状态”分开。

## 二、两个旧实现失败例子

第一个回归测试从当前全局状态取得快照，再把其中 Python 字段换成另一份有效状态，NumPy 字段改成无法识别的内容。调用旧恢复函数之后，异常确实出现，但 Python 全局状态已经不同。测试比较 Python 状态元组、NumPy 状态数组和 Torch 状态字节，发现局部副作用，而不是只断言函数抛错。一个操作报了错，并不自动意味着它没有改变任何东西。

第二个测试用真实小模型保存第二步检查点，把 RNG 版本改成不支持的值，同时在指标末尾追加尚未提交的字节。旧入口恢复第三步时，先执行日志回退，再遇到 RNG 版本错误。目录内容比较发现新增了恢复备份、活动日志也变了。备份本身并不错误，问题是这个请求根本无法继续训练，却已经触发了一项原本可以避免的文件修改。

## 三、独立生成器是关键抽象

校验 Python 状态可以创建一个单独的 random.Random 实例，尝试把待恢复状态设置到这个实例。NumPy 使用独立 RandomState，Torch 使用 CPU Generator。它们分别负责验证当前库所接受的状态格式，但不是程序随后用于训练的全局生成器。探针采用固定初始化值，不读取全局随机序列，因此检查一份 checkpoint 不会导致下一次训练抽样偏移。

这比“先设置全局状态，失败后再恢复原值”更直接。后一种方案即使最终回滚，也可能在两次设置之间暴露中间状态，尤其是同进程还有其他逻辑读取全局生成器时。本版没有创建回滚事务，而是把可预先发现的格式错误隔离在临时对象中。临时对象结束后即可丢弃，不需要将其持久化，也不需要增加一种新的随机状态序列化格式。

## 四、在原模块内扩展而不是另建系统

已有 training/rng_state.py 已经拥有捕获和恢复职责，所以本版在同一小模块中增加 validate_rng_state。它接收原有快照，完成校验后返回顶层的新字典，将生成器张量规范到 API 所需的 CPU 位置。capture_rng_state 的键与版本保持不变；原有 restore_rng_state 则先调用校验，再按原顺序设置全局状态。

新增函数不读取训练目录，不加载模型，也不决定是否修理日志。训练入口只在 load_resume_state 读取 checkpoint 后增加校验调用，原来的实际恢复位置不移动。这种拆分不需要另一套 checkpoint manager，也不把文件事务、模型配置、tokenizer 身份和 RNG 混成一个巨大函数。每个 helper 仍可单独测试，失败原因也能明确落到随机状态字段。

## 五、版本和字段校验如何工作

缺失或者显式为 None 的 RNG 快照继续作为历史格式处理，不安装任何新状态。非空快照必须是字典，版本必须是当前支持的整数。这里不能让布尔值 True 因为在 Python 中与数字一比较相等而冒充版本号，也不接受浮点数形式的一。对这些不受支持的结构，直接给出 RNG state version 错误，保留原有测试使用的诊断关键词。

随后逐项检查 Python、NumPy、Torch CPU 和 CUDA 字段。缺键、空序列导致的索引错误、数据类型错误或库对状态内容的拒绝，会被归并为明确的 checkpoint RNG state 错误，并保留原始异常链。开发时的损坏矩阵就发现了一个具体差异：Python 对空状态元组抛出的是 IndexError，而不是 ValueError。修复针对实际错误类型，不通过修改测试要求隐藏它。

## 六、张量先检查形状，再交给生成器

Torch 的随机状态不是模型的浮点权重，而是一维字节张量。校验首先要求它是非空的一维 uint8 Tensor，再转到 CPU，然后交给独立 CPU Generator 做真正的状态加载检查。因此，一个虽然类型是 Tensor、但内容长度只有两个字节的假状态，仍会被底层状态格式检查拒绝。只验证 dtype 或只验证字段存在都不够。

规范化在设置全局生成器之前完成。checkpoint 读取时可能把张量映射到所选设备，模型张量需要这个设备映射，而随机状态 API 可能仍要求 CPU 字节。这里统一处理设备位置，不让 Python 与 NumPy 已经恢复之后才因为 Torch 状态的设备不对而失败。返回字典保留原有字段，额外元数据不被删除；校验不会就地改写传入字典中的 CUDA 容器形式。

## 七、CUDA 覆盖到哪里必须写清楚

CUDA 状态是可选字段。本版只检查它是否为列表或元组，其中每个元素是否满足非空一维字节张量的结构要求，并规范到 CPU。它不会为了验证 checkpoint 而初始化 GPU，也不会用 CPU Generator 去解释 CUDA 状态的实际字节格式。两种设备的生成器格式不能互相冒充，结构相似不代表可被同一个生成器加载。

原来的 CUDA 恢复逻辑仍只在运行时已经初始化时执行。已有测试使用 mock 检查捕获和设置调用，这些断言保持原样。新增测试还确认校验本身没有查询初始化状态、更没有调用初始化函数。这只证明结构和调用边界，没有在本机完成真实 GPU 轨迹复现，也没有增加 GPU 数量、驱动版本或设备兼容性验证。原生设备设置失败不属于本版的事务保证。

## 八、为什么加载时检查一次，恢复时还检查一次

加载器入口的检查主要保护整个训练流程：无效快照在模型创建、日志回退或新输出目录生成之前被发现。restore_rng_state 自己再检查，是为了保护直接调用这个 helper 的其他代码。不能要求所有调用者都记住先调用另一个函数，否则以后新增入口很容易绕过预检，让部分状态恢复的问题再次出现。

这种重复检查的对象很小，通常只是几份状态数组和字节张量，不是把整个模型重新加载两遍。实际恢复依旧放在初始化完成之后，保证正确请求接上原来的随机轨迹。两次检查都不使用全局生成器抽样，因而不会改变训练随机序列；是否真的没有变化，要通过对比测试证明，而不是仅凭函数看起来“只是检查”就下结论。

## 九、损坏矩阵不止检查一种异常

新增表驱动测试包含非字典输入、空字典、错误版本类型、缺失字段、损坏 Python/NumPy 状态、不合适的 CPU Tensor 和 CUDA 容器，共二十一组。作为输入的部分字段故意使用另一套有效种子对应的状态，确保如果代码过早安装了前面字段，后面的全局状态比较能够捕获变化。若所有字段恰好与当前全局相同，部分恢复错误就可能被测试掩盖。

每次拒绝之后都会比较全局 CPU 状态，覆盖 Python 的完整元组、NumPy 的算法标记、状态数组及其余位置字段，以及 Torch 的字节张量。另一个纯校验测试检查传入状态没有被改写：CPU 张量字节不变，原 CUDA 元组仍是元组，返回值则是新的规范化结构。有效状态还要通过实际后续随机数序列比较，避免出现“总是拒绝”也被称作安全的假修复。

## 十、真实入口的文件保护如何证明

同目录恢复测试保留整个运行目录的文件名字和原始字节，在 RNG 版本无效时要求这些内容完全不变。它涵盖了先前确实出问题的 history recovery 路径，而不是只 mock 掉恢复函数再断言未调用。另一项测试向新的输出目录恢复，并给出结构上像字节张量、实际长度不合法的 CPU 状态，要求模型构造没有发生，新目录没有创建，已有文件也不改变。

整条 CLI 在读取 checkpoint 之前仍按既有行为设置随机种子，因此不能把 helper 的纯校验保证说成“整个失败命令不改变进程 RNG”。这两个范围必须分开：validator 和因格式错误拒绝的 restore 不改变全局 CPU 生成器；main 的历史初始化步骤仍存在。文件不改动是加载失败路径的承诺，进程中所有其他状态绝对不变则不是本版提供的语义。

## 十一、与上一版的独立进程对比

仅在一个 Python 进程里连续运行两个函数，有可能漏掉导入和初始化顺序造成的差异。所以独立对比从 Git 中取出 v1317 的训练脚本与 RNG helper 原始内容，让旧入口真正使用旧 helper。先保存第二步，再分别用旧版与当前版本恢复到第三步，保持语料、种子、模型结构、dropout、评估安排和采样设置一致。

对比的对象是完整 checkpoint 数据及指标、摘要、sample、tokenizer 文件字节，而不是只观察 loss 看起来差不多。之后在当前分支中破坏随机状态并附加未提交日志，使用独立命令行进程执行恢复，要求非零退出且全部运行文件保持原样。这样有效路径的等价性与无效路径的保护分别获得证据，也避免把恢复失败误写成模型质量变化。

## 十二、交付门与剩余边界

本版完整回归包含新增检查和之前的随机续跑、文件保存、日志恢复、分词器配对、参数预检、模型 CLI 与架构边界测试。Ruff 和严格 mypy 检查被修改的生产 helper，全部快速 CI 命令在本地运行，原有完整覆盖率入口在同提交 GitHub CI 通过之后才创建发布标签。既有测试期望、fixture、科学判定与覆盖率门槛不修改，远端结果也不能在运行之前预填。

最强的质疑是：既然调用底层生成器，是否就能保证任何随机状态都安全？不能。这里使用的是当前库接受的受信任检查点状态格式，不负责恶意 pickle、并发修改生成器、硬件故障或底层运行时崩溃；没有在未知异常之后提供跨设备回滚。它解决的是可提前检测的状态损坏，不把这个范围扩大为完整的事务或安全隔离系统。

复核可以从 `python -B -m unittest tests.test_rng_validation tests.test_rng_state tests.test_resume_rng -v` 开始，再执行工作流原来的完整测试入口。工程讲解和机器摘要属于项目公开交付，个人面试讲解仍留在本地。临时脚本和小模型只用于本次比较，证据记录后清理，不保留无用的后台进程。

一句话总结：先用独立生成器确认快照能被解释，再在正确续跑边界安装状态，让一次损坏的 RNG 读取不再先改日志、再留下半恢复的全局随机序列。
