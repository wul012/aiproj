# v1319：恢复的不只是模型，还要确认它吃的还是那份数据

## 一、前几版留下的最后一个安静偏差

v1315 已经把 tokenizer 的语义绑定到 checkpoint，v1318 又会在安装随机状态以前验证快照格式。这样可以发现词表含义被替换，也可以阻止损坏的随机字节先改动全局生成器。但训练入口仍只把数据路径当作输入线索，没有把实际加载的文本和划分比例记录进 checkpoint。用户把原文件改了几个字符，或者恢复时换一个 train_ratio，只要词表大小和模型配置还能对上，程序就会继续跑。

这种行为不一定立即报错。字符 tokenizer 甚至可以把新字符编码成 unknown，loss 仍然是一个浮点数；同样的文本换一个比例，模型也能从相同权重继续更新。结果看起来像“正常续训”，实际却已经不是原实验的随机轨迹或数据分布。本版把问题限定为数据漂移护栏，不修改数据读取算法、不重新设计分片，也不把工程校验写成模型质量结论。

## 二、旧代码的红灯样例

测试先用正常短文本训练到第二步。随后在文本末尾再增加一个已有词表中的字符，保证 tokenizer 的 `vocab_size` 和 token 映射仍然看起来完全合理。旧入口没有任何数据绑定字段，因此会继续恢复并写第三步；测试期待一个明确的 data binding mismatch，却没有得到异常。这证明只比较词表仍然抓不住训练语料变动。

第二个场景保持文本字节不变，只把恢复命令的 `train_ratio` 从 0.5 改成 0.6。旧 checkpoint 没有记录这个比例，训练和验证张量会按另一种边界切分，程序却照常执行。新测试还准备了同样内容的 alternate path，显式恢复到新输出目录，要求它成功。路径不是数据身份的一部分，用户有意分支时不应因为换了文件位置而被无理由拒绝。

## 三、绑定对象为什么是加载后的原始文本

数据可以来自 `--data`、`--prepared-data` 或 `--data-dir`。这些入口在 train.py 中都会先形成一个最终用于 tokenizer 的 `text` 字符串，然后才编码和分片。绑定直接对这个已加载文本的 UTF-8 字节计算摘要，因而覆盖三种入口的实际训练内容，而不是猜测某个 CLI 参数如何指向文件。

如果只哈希路径，文件内容变化时不会被发现，路径改名却会被误判为不兼容。如果只哈希 token id，又必须把 tokenizer 的身份和未知字符规则混进来，而且会让同一个文本在 tokenizer 版本改变时难以区分责任。本版把职责拆开：v1315 负责 token 语义，v1319 负责文本内容和切分比例。两者都使用可选字段，缺字段时保留旧格式行为。

绑定对象包含 version、text_sha256、text_length 和 train_ratio。摘要已经足以发现长度变化，但显式保留长度便于审阅者理解报告和快速定位差异；比例则是独立的数值字段，即使文本摘要相同也能拒绝另一种 train/validation 分割。规范对象不包含路径、文件修改时间或机器绝对路径，避免把展示层信息误当成训练语义。

## 四、为什么连 train_ratio 也要绑定

训练入口的随机 batch 从 train_data 和 val_data 中抽取。比例变化不只影响评估集，它也可能改变训练集的最后边界和可抽样起点。模型参数、optimizer 和 RNG 完全相同，在不同长度的张量上取 batch，后续更新自然会分叉。如果只保存文本摘要，用户仍能悄悄换比例而得到一条看似连续、实际不可比的轨迹。

本版把比例保存为 argparse 解析后的浮点值，不自行四舍五入或钳制。v1317 的前置校验已经确保它严格位于零和一之间，因此同一命令的序列化值可以直接比较。数据集很小导致验证集回退到训练集的现有逻辑仍然在 split_token_ids 内执行；绑定记录的是用户请求的比例，不会把回退结果冒充成另一个比例，也不改动回退算法。

## 五、加载和校验的顺序

main 先按原流程读取文本，再加载 checkpoint 与 tokenizer，编码文本之后才有足够信息比较 data_binding。校验放在 split_token_ids、模型构造、history recovery 和输出目录写入之前。这样数据不匹配会在同目录日志还未被恢复、已有文件还未被重写时失败。它与 v1318 的 RNG 校验互补：checkpoint 结构先过随机状态检查，文本内容随后过数据身份检查。

加载器仍然保持只负责 checkpoint、tokenizer 和 GPTConfig 的职责，没有把文本路径硬塞进 load_resume_state 的接口。数据校验在 main 里使用已加载的 text 和当前命令的 ratio，避免破坏其他调用者已有的加载函数签名。保存时，训练已经完成的同一份 text 和 ratio 重新生成 binding，和模型状态一起进入 v1314 的原子 checkpoint 写入。

## 六、旧 checkpoint 兼容策略

历史文件没有 data_binding，程序无法知道它当时使用了什么文本字节或切分比例。升级时强制要求字段会让以前的教学实验和缓存无法读取；遇到缺失字段后根据当前文本补写一个摘要，则会把未知事实伪装成已经验证。实现因此在字段缺失时直接跳过校验，并在文档和机器摘要中明确“不具备追溯身份保证”。

新保存的 checkpoint 会带 version 1 对象，后续恢复才获得更强的漂移检查。测试从真实 tiny checkpoint 中先删除字段，再继续训练，确保兼容路径没有被新护栏误伤。另一个测试检查字段结构、长度和六十四位摘要，证明新增内容不是一个只在说明里出现、保存时却遗漏的概念。

这里严格区分缺少字段与字段内容为 null。缺少意味着旧格式确实没有记录；null 或缺键字典则属于存在但损坏的数据，不能当作主动关闭校验的开关。长度必须是非负整数，不能让与整数相等的浮点值或布尔值混过去；比例必须是合法有限区间内的数值。测试把版本、长度、摘要、额外字段和比例错误放进二十二组损坏输入，避免新增字段只有成功路径可用。

## 七、路径和分支的处理

同样的文本复制到另一个路径，内容摘要和长度不变，数据绑定应当通过。测试把 checkpoint 保留在 source 目录，复制 data.txt 到 alternate.txt，再显式将输出目录设置为 branch。branch 不会拿 source 的 history 进行恢复，因为 v1316 已定义不同输出目录不修复原日志；它从当前请求重新生成自己的输出，但使用相同训练内容和比例。

这种设计允许用户把一次运行复制成实验分支，同时阻止“原路径文件被悄悄改了但继续覆盖原 run”的情况。它并不试图管理文件系统的并发写入，也不推断用户是否有意开始分支。输出目录和 checkpoint 路径仍由 CLI 负责，data_binding 只回答“这次输入的内容是否与 checkpoint 记录一致”。

要特别区分“同数据换输出目录”和“有意换数据微调”。前者保持输入身份，仍可使用现有恢复入口；后者改变了本版绑定的内容，即使输出目录不同也会被拒绝。本版没有新增跳过开关，不把微调假装成精确续跑。这是新绑定检查点的接口边界，旧格式兼容路径也不应被当作日常绕过检查的方式。

## 八、失败必须没有副作用

同目录文本变更或比例漂移时，测试先在 metrics.jsonl 末尾追加一个未提交尾部，再记录整个临时目录的文件字节。恢复调用抛出 mismatch 后，目录映射必须逐项相等：没有 history backup、新目录、重写日志或新的训练配置。校验位置如果提前或延后一个阶段，都可能让 v1316 的回退机制先动作，这个字节断言能抓到顺序错误。

保存字段结构错误时也必须尽早失败。版本不是整数、摘要缺失或对象不是字典都不能被静默接受；实现只对字段存在的 checkpoint 执行版本和完整对象比较。它不捕获异常后打印“继续”，也不用当前文本替换 checkpoint 里的旧绑定。错误必须到达调用者，便于批处理工具将这次运行标记为失败而不是生成误导性的结果。

## 九、与 tokenizer 和 RNG 三种身份的分工

现在一个新 checkpoint 可能同时含有三类边界：tokenizer_sha256 说明 token id 的语义，data_binding 说明加载的文本和比例，rng_state 说明下一步随机序列。它们不是一个“大一统实验指纹”，也不能互相替代。文本相同但 tokenizer 被交换，需要 v1315 拦截；tokenizer 相同但文本被改，需要 v1319 拦截；字段结构损坏，则由 v1318 的 RNG 校验或本版对象校验拦截。

分开保存还便于旧格式逐步兼容。一个历史 checkpoint 可能只有模型和 optimizer，另一个可能已经带 RNG 但没有 tokenizer 或 data binding。每个可选字段都明确自己的保证范围，不因为其中一项存在就声称整个实验已完全可复现。工程证据中也分别列出缺字段边界，避免把多个局部护栏拼成未经验证的全局结论。

## 十、数据目录和规范化边界

`--data-dir` 会调用现有 build_prepared_dataset，把目录下文本按已有顺序合成 prepared text。v1319 对最终合成的 text 做摘要，因此同一组文件在相同准备规则下得到同一绑定；文件排序、递归策略和清洗细节仍由 data_prep 模块决定。本版不修改这些科学和工程约定，也不从目录列表自行生成第二个摘要。

摘要针对加载完成后的字符串，不是硬盘文件的原始字节。现有文本读取会把 CRLF 等换行转换成 Python 看到的形式，数据目录也有既定的准备过程；这些步骤发生在摘要之前。测试把同一文本文件从 CRLF 改成 LF，确认绑定不变，而实际加载文本中的空白、顺序或 Unicode 字符发生变化仍然会改变摘要。这里没有额外 strip 或 normalize，路径展示、报告 HTML 和 JSON 缩进也不参与绑定。

## 十一、测试和独立对比

本版新增九个测试方法，除了文本变化、比例变化、换路径、历史格式与保存字段，还检查同长度文本重排、损坏元数据、换行转换、prepared-data 和 data-dir 三种入口的一致语义。测试使用 unittest，不改旧 fixture 和期望，并在退出时恢复自身改动的全局 RNG。前几版的 RNG、日志、tokenizer 和 checkpoint 测试继续原样执行，不把重复覆盖的测试数累加成虚高总数。

独立进程对比从 Git 中取出 v1318 的 train.py，与当前入口在相同 CPU、种子、文本、模型参数、评估间隔和采样设置下运行。checkpoint 只允许多出 data_binding 一个键，其余原有键和值递归精确比较；metrics、sample、summary 和 tokenizer 则按文件字节比较。五次独立进程调用还分别验证同长度文本变化和比例变化的拒绝，要求非零退出且完整原运行目录字节不变。新增字段的存在不意味着可以放宽其他字段的比较。

## 十二、证据门和剩余问题

最终定向命令会包含 data_binding、新 RNG 校验、训练前置、日志恢复、checkpoint 保存、tokenizer、RNG 续跑、模型 CLI 与架构边界。Ruff、严格 mypy 和仓库全部快速门逐项执行；完整覆盖率使用 CI 同一入口和不变的 88.98% 门槛。若本地长测试被中断，只记录未完成，不把它改写为通过；同提交远端结果经过确认后才创建标签。

最强质疑是“文本 hash 是否等于数据可信？”不是。它只能发现当前加载文本与 checkpoint 记录不同，不能鉴别攻击者同时修改两边，也不验证优化器、硬件、数据来源或模型质量。它同样不能替代人工确认实验目的。准确说法是 accidental data drift guard，而不是签名、审计证明或生产数据血缘系统。

复核从 `python -B -m unittest tests.test_data_binding tests.test_rng_validation tests.test_train_preflight tests.test_history_recovery tests.test_checkpoint_io tests.test_tokenizer_binding tests.test_rng_state tests.test_resume_rng -v` 开始，然后执行 CI 原有完整命令。工程讲解和机器摘要记录实际输出，个人面试资料仍留在本地。所有本版临时脚本、工具和小模型在发布后清理。

一句话总结：v1319 让新 checkpoint 同时记住它对应的文本和切分比例，阻止“词表没变所以看起来能跑”的数据漂移悄悄改变续训轨迹。
